Generated from executable application code, migrations, routes, controllers, layouts, pages, jobs, scheduled tasks, and project documentation.
Repository documentation is retained as background design intent, but executable code is authoritative where they differ.

1. PRODUCT PURPOSE
------------------
Mission-Lokal is a Laravel/Inertia React Progressive Web App for barangay-level incident reporting, response coordination, resident identity verification, administrative operations, field personnel mission execution, blotters, announcements, documents, library resources, and inter-role notifications.

The core process is:
1. Resident registers and uploads a government ID.
2. An admin reviews and approves or rejects the resident registration.
3. The approved resident reports a concern.
4. The concern receives category, visibility, severity, duplicate, and response-plan processing or staff review.
5. Admin staff review the report and create or escalate a mission.
6. Personnel receive the assignment, acknowledge it, execute the checklist, and upload completion proof.
7. Admin verifies mission completion and publishes a resolution post where appropriate.
8. Residents see public feed updates, private case updates, resolution posts, notifications, and civic XP changes.

2. TECHNOLOGY AND APPLICATION SHELL
-----------------------------------
Backend: PHP/Laravel, Inertia.js, MySQL/PostgreSQL-compatible migrations using UUID and spatial fields. DomPDF generates civic-recognition certificates and quarterly operational report PDFs.
Frontend: React + TypeScript, Vite, Tailwind CSS, and shadcn-style UI components.
Maps: Leaflet components and map utilities.
Queues/cache: Laravel cache, queue, and database-backed queue tables.
Storage: Local/public Laravel storage for uploaded IDs, concern media, proof, avatars, documents, signatures, and resolution media.
PWA: public service worker, web manifest, installable assets, and offline-oriented library behavior.

3. USER ROLES AND ACCESS
------------------------
resident
- Registers, verifies identity, and logs in only after resident verification approval.
- Uses the resident feed, concern reporting, resolutions, documents, library, help assistant, announcements, calendar, profile/security, blotters, and notifications.
- Can modify only owned concerns, selected own profile data, privacy of a report subject to sensitive-concern restrictions, and own blotters/documents/profile actions.

personnel
- Field responder assigned by an admin.
- Uses personnel missions and calendar.
- Sees department context, shift context, and mission notifications.
- Can acknowledge, update status, turn over an eligible mission, toggle checklist items, and upload proof.
- Peace & Order Tanods may have morning, evening, or overnight shifts; turnover goes to an eligible Tanod in the next shift.

admin
- Full barangay operations for assigned barangay.
- Manages dashboard, notifications, map, report queue and desk intake, missions, personnel/departments, resident verification, profile edits, residents, blotters, calendar, announcements, documents/signatures/templates, library, audit logs, and settings.
- General admin and radio-room admin types exist.

super_admin
- Platform-level tenant operator.
- Manages barangays, radio-room and view-only administrators, barangay suspension appeals, admin/resident profile edit requests, and security-clearance requests.
- Has no barangay field unless assigned by platform data.

Additional admin modifiers:
- admin_type=general: general main administrator.
- admin_type=radio_room: radio-room administrator.
- is_view_only: restricts the user to view-only behavior.

4. AUTHENTICATION AND ACCOUNT LIFECYCLE
---------------------------------------
Resident login:
- The normal login is /login.
- A resident account requires resident-profile verification_status=approved before protected resident routes can be used.
- If unapproved, the user is routed to /verification/waiting.
- Login rate limiting and inactive-account handling are implemented by the login controller.

Separate admin/personnel login:
- /admin-personnel/login authenticates administrative and personnel users through a separate login page/controller.

Registration:
- /register accepts first name, optional middle name, last name, name extension, house/street, barangay/city/province, birthday, email, mobile, government ID, optional parent or guardian information, and privacy consent.
- Residents must be at least 12 years old.
- Parent name and parent contact are required when age is below 18.
- Government ID supports JPG, JPEG, PNG, or PDF up to 2 MB.
- The system rejects duplicate approved identity records based on normalized first name, last name, and birthday.
- It also rejects duplicate pending registrations with the same name and birthday.
- A barangay/city/province combination must match an active barangay.
- Successful registration creates a pending resident registration and waiting-verification flow.

Verification flow:
- Admin views resident verification queue and individual verification records.
- Admin can approve the resident after confirming supplied identity details.
- Admin can reject with a rejection reason.
- Approval permits access to protected resident routes.
- Government ID viewing uses a private admin route rather than exposing public media URLs.

Password and security:
- Forgot password requests email OTP; OTP verification then allows password reset.
- OTP request, verification, and reset routes are throttled.
- Temporary generated passwords can be replaced through /password/custom.
- Password prompts may be dismissed temporarily through /password/prompt/dismiss.
- Resident security settings support OTP request, OTP verification, and password update.
- Admin security settings can request OTP or a super-admin security-clearance key before sensitive password changes.

Session actions:
- /logout logs out authenticated users.
- Profile photos can be uploaded or deleted.
- Theme preferences are supported in the resident frontend.

6. RESIDENT MODULES AND ACTIONS
--------------------------------
Feed and concerns (/feed, /concerns/new, /concerns/{concern})
- Feed loads concerns available to the resident in public and permitted private contexts.
- Users can create a concern title, category/subcategory or selected concern type, description, visibility, location, address, and media.
- Sensitive categories/subcategories can force private visibility.
- Public reports can receive up/down-like voting through concern vote actions.
- Concern creator can change visibility between public/private when not locked by sensitivity.
- Creators can retract a submitted or rejected report before administrative processing; processing locks it.
- Concern detail displays a status timeline, response plan, proof summary, updates, and media when authorized.
- Concern cards show the reporter's highest permanently earned Civic XP badge when one exists.
- Concern visibility and private-media routes are access-controlled.

Rate limits:
- Concern submission: 30 requests per minute.
- Barangay-help chat: 10 requests per minute.

Resolutions (/resolutions):
- Shows public resolution posts and outcome information.

Blotters (/blotter/new, /blotter/new/{type}, /blotters, /blotter)
- User chooses one-party or two-party blotter flow.
- Fields and narrative are submitted to the resident blotter controller.
- Resident can view own blotter status/history.
- Admin approval creates/updates the administrative blotter record.

Announcements:
- /announcements lists published announcements.
- /announcements/{announcement} displays one announcement.
- Residents can join or leave volunteer announcements through the volunteer route.
- Event announcements may include event time.

Calendar:
- Displays barangay calendar events derived from announcements and operational calendar data.

Library:
- Displays prepared manuals, responder contacts, and FAQ/help content maintained by admins.
- Available content includes emergency and preparedness resources.

Barangay Help:
- /help renders the barangay help/chat page.
- /help POST sends a question to the BarangayChatController.
- The chat service uses current barangay FAQ/library context and rate limits requests.

Documents:
- Resident lists document templates and request queue.
- Resident submits a request to /documents/{template}.
- Resident views a generated/processed request through /documents/{documentRequest}.
- Document availability and requirements are controlled by admin templates and barangay document settings.

Profile:
- /profile displays resident summary, verification, current-month Civic XP, report counts, profile photo, and all permanently earned badges with their earned dates.
- Civic XP starts at 50 each month, resets on the 1st, and is capped at 100.
- Earned badges and their certificates are retained across monthly XP resets; residents can download each earned badge certificate at /profile/civic-certificates/{badgeId} or their highest badge at /profile/civic-certificate.
- /profile/edit displays editable fields.
- /profile/edit POST submits resident profile changes.
- Profile changes may enter admin approval instead of immediately overwriting protected identity data.
- /profile/security supports OTP and password changes.
- Photo upload and deletion are available to authenticated users.

Notifications:
- Resident notification page lists and provides notification state updates.

Verifications:

Profile edits:

Residents:

- Updates resident information.

Documents:

- CheckUnacknowledgedMissions checks mission acknowledgement deadlines.
- civic-xp:monthly-reset resets monthly Civic XP to 50 without deleting badges or event history.

16. CIVIC XP AND GAMIFICATION
------------------------------
Resident profiles start at 50 Civic XP each month. Scores reset to 50 at 00:01 on the first day of each month and cannot exceed 100.
- A staff-accepted valid concern awards category-based XP: Public Safety & Order 5, Infrastructure & Utilities 4, Sanitation & Environment 3, and Katarungang Pambarangay 2; other categories use the barangay setting capped at 5.
- There is no per-day award limit. Each accepted concern can award XP only once, and the monthly score remains capped at 100.
- civic_xp_monthly_rankings stores each month's final score, rank, badge list, resident name, and account ID per barangay.
- The scheduled monthly reset archives the closing month's ranking before resetting profiles. If an older month has events but no snapshot, the admin page reconstructs and stores it on first view; the page identifies the data source.
- Awards are recorded idempotently in civic_xp_events; spam/rejection penalties cannot reduce the score below zero.
- The admin ranking is barangay-scoped and sorts active verified residents by their current-month score.
- Five permanent badge tiers are earned at 60 (Civic Spark), 70 (Community Helper), 80 (Neighborhood Champion), 90 (Civic Advocate), and 100 (Civic Leader) monthly XP.
- Badges survive monthly score resets and appear on resident profiles and concern cards.
- Residents can download a one-page A4 landscape certificate as PDF or PNG for their highest badge from /profile/civic-certificate; admins can download either format from the civic-recognition ranking.
- Residents can view their full permanent badge history and download an individual PDF or PNG certificate for each earned badge.

18. SECURITY AND PRIVACY CONTROLS
---------------------------------
- Protected routes use auth, role middleware, resident verification middleware, and super-admin middleware.
- Private concern/proof/media endpoints authorize the user against the protected case or ownership.
- Government IDs and private media are not expected to be public paths.
- Sensitive concern categories force private visibility.
- Destructive reports are locked once under active processing.
- Account/password routes are throttled.
- Settings password changes can require OTP or clearance key.
- Suspended barangays are excluded from normal public/active operations by middleware/application redirects.
- Audit logging records privileged actions in implemented admin controllers.
- Profile photo, media, and government IDs use storage keys rather than trusting arbitrary client paths.

19. REAL-TIME VS CURRENT IMPLEMENTATION NOTE
---------------------------------------------
The frontend and backend currently implement server-rendered Inertia navigation, forms, flash messages, polling-like reloads, notifications, and scheduled Laravel jobs. A dedicated WebSocket/push server is not established merely by mentioning real-time recommendations in the blueprint. SMS, geocoding, AI behavior, and third-party services are implemented only where corresponding service/controller/job code exists; the presence of configuration fields does not prove an active external provider.
